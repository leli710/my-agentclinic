# מפרט פיצ'ר — Agents and Ailments

**סטטוס:** מומש מקומית; מפרטי הדרישות, התוכנית והאימות נורמלו מחדש ב־2026-11-14<br>
**מפרטי הדרישות, התוכנית והאימות:** `specs/2026-11-14-agents-and-ailments/`<br>
**מטרת הפיצ'ר:** ניהול סוכני תוכנה ותיעוד התקלות, חומרתן והטיפולים שבוצעו בהם.

## רקע והיקף

הפיצ'ר מוסיף ל־Agent Clinic מסד SQLite מקומי וממשק Web בעברית וב־RTL. המערכת מנהלת יומן תחזוקה ידני לסוכני תוכנה. אין בה הפעלה או אבחון אוטומטי של סוכנים.

## ישויות ושדות

### Agent — סוכן תוכנה

- `id`: מזהה מספרי חיובי שנוצר על ידי SQLite.
- `name`: חובה, אחרי trim באורך 2–80 תווים.
- `description`: אופציונלי, עד 500 תווים.
- `status`: `active` או `inactive`; ברירת המחדל `active`.
- `created_at`, `updated_at`: תאריכים בפורמט UTC/ISO.

השבתת סוכן היא רכה כדי לשמור על קישור לרשומות תקלה; לא מוחקים סוכן עם היסטוריה.

### Ailment — תקלה בתוכנה

- `id`: מזהה מספרי חיובי.
- `agent_id`: חובה, מזהה של סוכן קיים.
- `title`: חובה, אחרי trim באורך 3–120 תווים.
- `description`: חובה, אחרי trim באורך 3–2000 תווים.
- `severity`: אחת מ־`low`,‏ `medium`,‏ `high`,‏ `critical`.
- `status`: אחת מ־`open`,‏ `in_progress`,‏ `resolved`; ברירת המחדל `open`.
- `treatment`: אופציונלי, עד 2000 תווים.
- `outcome`: אופציונלי, עד 2000 תווים.
- `created_at`, `updated_at`: תאריכים בפורמט UTC/ISO.

## זרימות משתמש

1. **Dashboard (`GET /`)** — סיכום סוכנים פעילים, מספר תקלות פתוחות, תקלות לפי חומרה ורשומות אחרונות. מצבי ריק מקשרים להוספת סוכן.
2. **סוכנים (`GET /agents`)** — רשימת סוכנים וטופס הוספה.
3. **יצירת סוכן (`POST /agents`)** — אימות קלט, שמירה ב־SQLite והפניה חזרה לרשימה; קלט לא תקין מוצג עם הודעה ברורה.
4. **פרטי סוכן (`GET /agents/:id`)** — פרטי הסוכן ורשימת התקלות המשויכות.
5. **הפעלה/השבתה (`POST /agents/:id/status`)** — שינוי מצב ללא מחיקה.
6. **תקלות (`GET /ailments`)** — רשימה עם סינון אופציונלי לפי `status` תקין.
7. **פתיחת תקלה (`POST /ailments`)** — יצירת תקלה המשויכת לסוכן פעיל קיים; ולידציה של שדות, חומרה ותיאור.
8. **עדכון תקלה (`POST /ailments/:id/update`)** — עדכון מצב, חומרה, תיאור הטיפול והתוצאה.
9. כל עדכון טופס תקין משתמש ב־Post/Redirect/Get. אין להחזיר הצלחה אם השמירה נכשלה.

## ממשק ונגישות

- מסמך HTML סמנטי עם `<header>`,‏ `<nav>`,‏ `<main>` ו־`<footer>`.
- רכיבי Header, Main ו־Footer המשותפים נשמרים בקבצים נפרדים תחת `src/views/`.
- `lang="he"` ו־`dir="rtl"` ברמת `<html>`.
- טקסטים, הודעות ולחצנים בעברית.
- Pico CSS מקומי, ללא CDN, וללא גופנים או תמונות חיצוניים.
- תצוגה רספונסיבית במסכים צרים; טפסים וטבלאות לא מרחיבים את העמוד מעבר לרוחב החלון.
- כל ערכי המשתמש מוצגים כטקסט מקודד; אין להחדיר קלט לטקסט HTML לא מסונן.

## מסד נתונים ו־Migrations

- `better-sqlite3` כתלות ישירה בגרסה מדויקת, SQLite מקומי בקובץ `data/agent-clinic.sqlite`.
- SQL migrations ממוספרות בספרייה `migrations/`; טבלת `schema_migrations` מתעדת אילו migrations הוחלו.
- אכיפת foreign keys ואינדקסים לשדות סינון.
- migration נכשלת אם SQL אינו תקין; אין להמשיך בהפעלה כאילו הצליחה.
- נתוני דוגמה פיקטיביים נוצרים רק במסד ריק, ולא משוכפלים בכל הפעלה.

## תוכנית עבודה

1. להתקין ולנעול גרסאות תלויות מדויקות: `better-sqlite3`, הטיפוסים שלו ו־Pico CSS.
2. ליצור מודל TypeScript עצמאי ל־Agent ול־Ailment.
3. לכתוב migration ראשוני עם constraints, foreign key ואינדקסים.
4. לממש את חיבור SQLite, runner ל־migrations, repository ונתוני דוגמה.
5. לחלץ טיפוסי Props לתצוגות, כדי לא לערבב נתוני persistence עם פרטי רינדור.
6. ליצור תצוגות רספונסיביות בעברית עם Pico CSS מקומי.
7. לממש Dashboard, מסכי סוכנים, מסכי תקלות וטפסי שינוי מצב.
8. להוסיף בדיקות Vitest ל־migrations, persistence, ולידציה וזרימות HTTP.
9. להריץ `npm ci`,‏ Build, בדיקות ובדיקת דפדפן/HTTP מקומית.
10. לבצע השוואה בין דרישות המפרט למימוש ולעדכן את ה־Roadmap.
